# VetDietDerm

Ветеринарный менеджер для ведения пациентов, приёмов и повторных наблюдений. Первый целевой сегмент продукта — ветеринарные дерматологи и диетологи; архитектура и пользовательские сценарии должны позволять подключать другие специализации без создания отдельных приложений.

> Статус: функциональный прототип в процессе продуктового pivot. Текущая версия уже содержит часть CRM, клинической истории, дерматологической галереи и диетологических инструментов. Ближайшая цель — собрать их в единый рабочий контур ветеринарного специалиста.

## Продуктовая идея

VetDietDerm должен стать главным рабочим окном врача на протяжении всего цикла лечения:

1. Администратор или врач записывает клиента и пациента.
2. Врач открывает приём из расписания и заполняет структурированный анамнез.
3. Во время приёма добавляются результаты осмотра, диагнозы, назначения, изображения и анализы.
4. Расчёты рациона, дозировок и инфузии сохраняются в контексте приёма.
5. После приёма система помогает провести повторный контакт и оценить динамику.

Продукт не заменяет клиническое решение врача. Калькуляторы, подсказки и AI-функции должны показывать исходные данные и оставлять окончательное решение специалисту.

## Для кого

### Первый сегмент

- частнопрактикующие ветеринарные дерматологи и диетологи;
- небольшие специализированные кабинеты и клиники;
- ассистенты и администраторы, которые ведут запись и коммуникации.

### Расширение

После проверки основного сценария продукт сможет подключать терапевтов и другие специализации через новые шаблоны приёма, справочники и калькуляторы. Ядро — клиент, пациент, запись, приём и медицинская история — остаётся общим.

## Основные модули

### 1. Клиенты и пациенты

- создание и редактирование владельца и одной или нескольких карточек животных;
- контакты, предпочтительный канал связи и согласия владельца;
- вид, порода, пол, дата рождения, вес, BCS, аллергии, хронические состояния;
- краткая клиническая сводка и единая хронология событий;
- быстрый поиск и защита от дублей.

### 2. Приёмы и анамнез

- создание приёма из записи или непосредственно из карточки пациента;
- состояния `черновик`, `в работе`, `завершён`, `подписан`;
- структурированный анамнез, осмотр, оценка, диагнозы, план и назначения;
- шаблоны первичного, повторного, дерматологического и диетологического приёма;
- пользовательские шаблоны с версиями и обязательными полями;
- перенос ключевых показателей в динамику пациента.

Для дерматологии приоритетны жалоба, длительность симптомов, VAS, локализация поражений, сезонность, обработки, диета, цитология/соскобы и фотодинамика. Для диетологии — текущий рацион, лакомства, ограничения, активность, BCS/MCS, цель и контрольные показатели.

### 3. CRM и расписание

- календарь врача и клиники: день, неделя, список;
- создание, перенос и отмена записи;
- статусы `запланирована`, `подтверждена`, `ожидает`, `на приёме`, `завершена`, `не явился`;
- напоминания и журнал коммуникаций;
- задачи на повторный контакт и контрольный приём;
- фильтры по врачу, типу приёма и статусу.

### 4. Галерея и медицинские файлы

- фотографии, результаты анализов, PDF и другие вложения;
- привязка к пациенту и конкретному приёму;
- дата исследования, категория, подпись, область тела и теги;
- сравнение фотографий и показателей в динамике;
- безопасное хранение оригинала и превью без записи base64 в основную БД.

### 5. Клинические калькуляторы

- рацион: RER/MER, потребность в энергии, состав и порции;
- препараты: доза на массу, концентрация, объём и кратность;
- инфузия: дефицит, поддержка, потери, скорость и общий объём;
- единицы измерения, округление и предупреждения о неполных данных;
- сохранение исходных параметров, результата и версии формулы в приём.

Любая формула перед выпуском должна пройти клиническую проверку. Результат обязан быть воспроизводимым и содержать источник или версию методики.

## Текущая реализация

На split stack (Next.js в `frontend/`, FastAPI в `apps/api/`, PostgreSQL) уже есть:

- клиент и пациент как отдельные сущности;
- приёмы с анамнезом, SOAP и VAS;
- расписание записей;
- дерматологическая фотогалерея (файлы на диске, метаданные в PostgreSQL);
- журнал коммуникаций;
- планы питания и оценка по FEDIAF 2025.

Пока не входят: пользователи и роли, портал владельца, knowledge/AI, drug checker, калькуляторы дозы и инфузии.

## Что меняется в результате pivot

### Продукт и навигация

Основная навигация должна отражать ежедневную работу: **Сегодня**, **Расписание**, **Пациенты**, **Приёмы**, **Файлы**, **Калькуляторы**, **Шаблоны**, **Настройки**. Диетология и дерматология становятся наборами специализированных шаблонов и инструментов внутри общего менеджера, а не изолированными разделами.

### Доменная модель

Потребуются следующие сущности и связи:

- `Workspace/Clinic`, `User`, `Membership`, `Role` — организация, сотрудники и доступ;
- `Client` — владелец с контактами, согласиями и несколькими пациентами;
- `Patient` — животное и его медицинские атрибуты;
- `Appointment` — слот в расписании, ответственный врач и статус;
- `Encounter` — самостоятельный медицинский приём, при необходимости связанный с записью;
- `EncounterTemplate` и `TemplateVersion` — схема анамнеза и осмотра;
- `ClinicalEntry` — диагноз, назначение, показатель или заметка;
- `Attachment` — универсальный медицинский файл с метаданными;
- `Calculation` — входные данные, формула, результат и версия;
- `Task`, `Reminder`, `Communication` — CRM-действия;
- `AuditEvent` — история значимых изменений.

Существующие `Pet`, `Consultation` и `LesionPhoto` должны быть мигрированы, а не удалены без переноса данных.

### Техническая основа

- перейти от single-user прототипа к multi-user модели с аутентификацией и разграничением ролей;
- использовать PostgreSQL для локальной разработки и production (Neon на Vercel);
- вынести файлы в S3-совместимое объектное хранилище;
- добавить валидацию API, миграции, тесты критических формул и аудит;
- хранить даты в UTC и отображать в часовом поясе клиники;
- локализовать интерфейс и клинические справочники независимо;
- сделать специализированные возможности подключаемыми пакетами, а не полями общего пациента.

## Границы первого MVP после pivot

В MVP входят:

- один врач или небольшая клиника;
- клиенты и пациенты без дублей;
- календарь и базовые CRM-статусы;
- структурированный дерматологический и диетологический приём;
- фото и документы в истории пациента;
- проверенные калькуляторы рациона, дозы и инфузии;
- экспорт заключения и резервное копирование;
- роли врача и администратора, журнал критичных действий.

Пока не входят: склад, закупки, полноценный биллинг, лабораторные интеграции, телемедицинская платформа и автоматическая постановка диагноза. Они не должны блокировать развитие ядра.

## Критерии успеха pivot

- врач может провести типовой приём без параллельного ведения данных в таблицах и заметках;
- медианное время оформления приёма сокращается;
- большинство завершённых приёмов имеют заполненный структурированный анамнез;
- повторная запись создаётся из завершённого приёма без повторного ввода данных;
- расчёты и вложения доступны в истории и однозначно связаны с приёмом;
- новые специализации добавляются через конфигурацию и шаблоны без изменения ядра пациента.

## Технологии прототипа

- Next.js 16, React 19, TypeScript;
- Tailwind CSS и shadcn/ui;

## Локальный запуск

### Docker Compose с существующим PostgreSQL

Compose запускает FastAPI и Next.js. PostgreSQL должен быть уже создан и доступен из контейнера API.

```powershell
Copy-Item .env.example .env
# Заполните DATABASE_ADDRESS, DATABASE_PORT, DATABASE_NAME,
# DATABASE_USER, DATABASE_PASSWORD и INSTANCE_PASSWORD в .env.
docker compose up -d --build
```

Для PostgreSQL на компьютере с Docker задайте `DATABASE_ADDRESS=host.docker.internal` и опубликованный порт базы (в примере `15432`). Для удалённой базы укажите её DNS-имя/IP и порт (обычно `5432`). `127.0.0.1` внутри контейнера указывает на сам контейнер. PostgreSQL должен разрешать соединения из сети Docker.

`DATABASE_SSLMODE` по умолчанию — `prefer`; для сервера, требующего TLS, задайте `require` или подходящий режим проверки сертификата. Пароль можно записать в одинарных кавычках, чтобы Compose не подставлял переменные вместо символов `$`. Спецсимволы в пароле кодировать как URL не нужно.

Перед запуском API автоматически выполняется `alembic upgrade head` для указанной базы. Frontend запускается после успешной проверки API и подключения к БД. Вложения сохраняются в постоянном томе `attachments`; существующие локальные файлы из `data/attachments` в него автоматически не переносятся.

Интерфейс: `http://127.0.0.1:3000`, API: `http://127.0.0.1:8000`. При доступе с другого компьютера укажите адрес сервера в `NEXT_PUBLIC_API_URL` и `FRONTEND_URL`. После изменения `NEXT_PUBLIC_API_URL` пересоберите frontend: `docker compose up -d --build frontend`.

Логи: `docker compose logs -f`. Остановка: `docker compose down` (том вложений сохраняется).

### Без Docker

Стек: Next.js UI в `frontend/`, FastAPI в `apps/api/`, PostgreSQL на `127.0.0.1:15432`. Нужны Node.js 20+ и Python 3.13+ (`uv`).

```bash
cp .env.example .env
# заполните DATABASE_* и INSTANCE_PASSWORD
# для PostgreSQL на этом компьютере: DATABASE_ADDRESS=127.0.0.1

# API
uv sync --project apps/api
uv run --project apps/api alembic -c apps/api/alembic.ini upgrade head
uv run --project apps/api python -m vetdietderm_api.main

# UI (второй терминал)
npm install --prefix frontend
npm run dev
```

`NEXT_PUBLIC_API_URL` читается из корневого `.env` или из `frontend/.env`. UI: `http://127.0.0.1:3000`. API: `http://127.0.0.1:8000`.

API также читает `apps/api/.env`, значения которого имеют приоритет над корневым `.env`. Старый `DATABASE_URL` поддерживается и имеет приоритет над отдельными `DATABASE_*`; удалите его из env при переходе на новый формат. В Docker локальные env-файлы не копируются в образы, параметры передаёт Compose.
