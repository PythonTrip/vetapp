**Audit result:** The deployed split stack (Next.js UI, FastAPI, PostgreSQL, on-disk attachments) enforces a single instance-password gate and persists the main clinical records, but two list contracts silently drop records the UI treats as complete. After 200 older appointments the schedule-to-encounter path cannot open a recent visit, and related picker/link invariants can leave encounters unlinked or reverted from completed to draft.

### Actors and Workflows

- **Actors:** anonymous browser (HTML shell, `/health`, OpenAPI); clinic staff sharing one instance password; Docker healthcheck calling `/ready`; Alembic running inside the API container at start. No distinct users, roles, or background workers.
- **Core workflows traced:** create/search client and patient; book and edit a schedule slot; start/save/complete an encounter from a slot or from a patient; log a communication; upload/download/delete an attachment; apply clinic/doctor templates; assess a ration and save/read a diet plan snapshot.
- **Privileged or destructive workflows:** delete appointment, encounter, communication, attachment, non-standard template, and clinical-catalog item; replace food nutrient values; instance-password login.
- **Money, quota, entitlement or capacity paths:** not applicable (no billing). Attachment size and list windows are the only capacity limits implemented.

### Business Invariants and State

- **Ownership / tenant invariants:** single clinic database; appointment and attachment `encounter_uuid` must belong to the same patient when that field is written; communications copy `client_uuid` from the patient at create time.
- **State transitions:** encounter `draft` / `in_progress` / `completed` with no server-side machine; UI writes `draft` or `completed`. Appointment `scheduled` / `completed` / `cancelled` / `no_show`. Deleting an encounter sets appointment/attachment `encounter_uuid` to null.
- **Consistency / uniqueness:** food nutrient identity unique on `(food_uuid, nutrient_uuid, basis, source_uuid)`; no uniqueness for client/patient names; diet-plan reads return the stored snapshot without recomputation.
- **Idempotency / repeated delivery:** no webhooks; HTTP retries are last-write-wins on PATCH; diet-plan PATCH recomputes and replaces the snapshot.
- **Concurrency-sensitive state:** check-then-act on encounter ownership when `encounter_uuid` is present; appointment patient change does not re-validate an existing link; encounter autosave races the encounters query cache after complete.
- **Time / expiry / ordering:** timestamptz columns; UI converts `datetime-local` through the browser timezone; schedule day filter uses local start/end converted to ISO.

## Error Map

### AUD-001 — Opening a recent appointment’s encounter shows an empty workspace once 200 older slots exist

- **Severity:** `high`
- **Category:** `functional correctness`
- **Location:** `apps/api/src/vetdietderm_api/appointments/repository.py:41` — `list_appointments`; `frontend/src/components/clinical/encounter-workspace.tsx:106-130` — `useAppointmentsQuery()` without a date window
- **Evidence:** `list_appointments` always `order_by(Appointment.starts_at.asc()).limit(200)` even when `from`/`to` are omitted. The encounter workspace loads that unfiltered list and resolves `?appointmentId=` with `appointments.data.find`. `GET /appointments/{appointment_id}` exists on the API but is unused by the UI. The schedule board queries a single local day, so today’s row still appears there.
- **Demonstrated invariant / expected behavior:** Product and UI copy treat “Начать приём” / “Открыть приём” from a visible schedule row as opening that slot’s encounter (`README.md` schedule→encounter flow; `schedule-board.tsx` link to `/encounter?appointmentId=`).
- **Trigger scenario:** The clinic accumulates 201 or more appointments. A doctor opens today’s (newer) slot from Расписание.
- **Execution / data path:** Schedule `GET /appointments?from=&to=` returns the day. Navigation sets `appointmentId`. Encounter page `GET /appointments` returns the 200 earliest rows. `selectedAppointment` is null, so the workspace stays on “Выберите запись или пациента” and never loads or creates the linked encounter.
- **Broken behavior:** The unfiltered list is an oldest-first window, so the appointments a doctor is starting today are the first to fall out. The UI still offers the action from the day view.
- **Impact:** Core same-day encounter workflow fails after modest production volume (on the order of a few months at a handful of visits per day). The doctor cannot continue the documented schedule-linked visit; a workaround “без записи” creates an unlinked encounter.
- **Recovery / workaround:** Create the encounter without the appointment, then manually hope a later save relinks if the slot is still in the truncated list. Deleting historical appointments would also restore the window. Neither preserves the intended link reliably.
- **Recommended fix:** Fetch `GET /appointments/{id}` (and the patient/encounter by id) for the query-string target. Change the unfiltered list to newest-first or require a date window, and stop treating a capped list as the full set.

### AUD-002 — Saving a schedule row after changing the patient leaves the slot pointing at another patient’s encounter

- **Severity:** `medium`
- **Category:** `state/data integrity`
- **Location:** `apps/api/src/vetdietderm_api/appointments/repository.py:71-89` — `update_appointment`; `frontend/src/components/clinical/schedule-board.tsx:119-129` — save payload
- **Evidence:** `_validate_encounter` runs on create and only when `encounter_uuid` is present in the PATCH body. Schedule save always sends `patient_uuid` and never sends `encounter_uuid`. Changing the patient therefore updates `appointments.patient_uuid` while leaving the previous `encounter_uuid` in place. Create-time checks and attachment upload still reject cross-patient encounters.
- **Demonstrated invariant / expected behavior:** An appointment’s encounter must belong to the same patient (`_validate_encounter` / HTTP 400 `"Приём принадлежит другому пациенту"`).
- **Trigger scenario:** Edit a slot that already has `encounter_uuid`, choose a different patient in the dialog, save.
- **Execution / data path:** `PATCH /appointments/{id}` with `{ patient_uuid, starts_at, duration_min, visit_type, status, notes }`. Repository sets the new patient, skips encounter validation, commits. Schedule shows patient B with “Открыть приём”. Encounter workspace then loads patient B’s encounters, does not find A’s encounter, and presents a blank form. The next successful encounter save writes a new `encounter_uuid` for B and unlinks A’s visit from the slot (`ondelete=SET NULL` only if the encounter row is deleted; here the FK is overwritten).
- **Broken behavior:** Durable appointment state violates the same-patient rule the write path already implements for other fields.
- **Impact:** The calendar labels the wrong patient against an existing clinical encounter. Opening the slot does not show the original notes. A subsequent autosave can re-point the slot at a new blank encounter for the new patient, leaving the original visit detached from the schedule.
- **Recovery / workaround:** Do not change patient on a linked slot; create a new appointment instead. Repair is a manual PATCH that either clears `encounter_uuid` or restores the original `patient_uuid`.
- **Recommended fix:** Whenever `patient_uuid` changes, re-run `_validate_encounter` on the stored `encounter_uuid` (or clear the link). Persist `encounter_uuid` from the editor, or omit `patient_uuid` on updates that are not meant to reassign the animal.

### AUD-003 — Schedule and encounter patient pickers omit anyone outside the 50 most recently updated patients

- **Severity:** `medium`
- **Category:** `functional correctness`
- **Location:** `apps/api/src/vetdietderm_api/patients/repository.py:10,85` — `LIST_CAP` / `search_patients`; `frontend/src/components/clinical/schedule-board.tsx:70,245` and `frontend/src/components/clinical/encounter-workspace.tsx:107,397` — `usePatientsQuery("")`
- **Evidence:** Empty `q` still applies `order_by(Patient.updated_at.desc()).limit(50)`. The schedule dialog and encounter “без записи” select render only that array. Client-side search in the encounter header filters the already loaded 50. The patients page and nutrition picker send a typed `q` to the API, so they can reach other rows.
- **Demonstrated invariant / expected behavior:** Booking and starting a visit require selecting the intended patient from the operational pickers.
- **Trigger scenario:** The database contains 51 or more patients. The doctor books from Расписание or starts a visit without a slot, and the animal is not among the 50 last-updated cards.
- **Execution / data path:** `GET /patients?q=` → 50 rows → Select options. No second request by id except when an appointment already carried a nested `patient` object.
- **Broken behavior:** Those patients remain in PostgreSQL and on `/patients`, but cannot be chosen for a new appointment or a no-slot encounter.
- **Impact:** Core CRM intake fails for older/less recently edited animals once a small clinic exceeds 50 patients. Nutrition search is not affected the same way.
- **Recovery / workaround:** Open the patient card and save any change to bump `updated_at`, or type a search on Пациенты (still does not add them to the schedule select). No in-dialog search hits the API.
- **Recommended fix:** Give the schedule/encounter pickers the same server-side search as nutrition, or raise/paginate the list and fetch a patient by id when the UI already knows the uuid.

### AUD-004 — Completing a visit then typing again can autosave the encounter back to draft

- **Severity:** `medium`
- **Category:** `concurrency/idempotency`
- **Location:** `frontend/src/components/clinical/encounter-workspace.tsx:252-278,323-331` — `saveEncounter` status and autosave effect; `frontend/src/lib/hooks.ts:411-437` — encounters cache not updated from the mutation result
- **Evidence:** Complete sends `status: "completed"` then `invalidateQueries(["encounters", patientId])` without `setQueryData`. Autosave uses `editingRecord?.status === "completed"` from that cache. `lastPersistedForm` is updated on complete, so the next keystroke schedules autosave after 1100 ms with `finalize=false`, which writes `draft` while the cached row is still the pre-complete object. Appointment relink on autosave does not run if `encounter_uuid` already matches, so the slot can remain `completed`.
- **Demonstrated invariant / expected behavior:** “Завершить приём” persists `completed` and, for a linked slot, marks the appointment completed (`saveEncounter(true)` payload and toast).
- **Trigger scenario:** Doctor completes the visit, then edits a field (typo in complaint, extra diagnosis) before `GET /patients/{id}/encounters` returns.
- **Execution / data path:** `PATCH /encounters/{id}` completed → cache still `draft`/`in_progress` → user input → 1100 ms timer → `PATCH` with `status: "draft"`. Schedule query may still show a completed appointment.
- **Broken behavior:** The visit is no longer completed in the clinical record while the calendar can still say the slot is done.
- **Impact:** Later review and any workflow that depends on encounter status see a draft. The doctor may believe the visit was signed off.
- **Recovery / workaround:** Click “Завершить приём” again after the encounters query refreshes. Waiting for the list refetch before editing also avoids it.
- **Recommended fix:** Derive write status from the last successful `saved.status` (or `setQueryData` with the mutation result), not from a stale list cache. Do not send `draft` after a completed save unless the user explicitly reopens the visit.

### AUD-005 — A larger-than-8 MiB upload is fully buffered before rejection and can exhaust the API process

- **Severity:** `medium`
- **Category:** `material performance`
- **Location:** `apps/api/src/vetdietderm_api/attachments/repository.py:64-68` — `create_attachment`; `apps/api/src/vetdietderm_api/attachments/storage.py:8` — `MAX_ATTACHMENT_BYTES`
- **Evidence:** After content-type checks, the handler `upload.file.read()`s the entire part, then compares `len(payload)` to 8 MiB and may return 413. No Starlette/FastAPI max-body setting exists in the app or Compose command. The Next proxy streams the same request body to FastAPI (`frontend/src/app/api/[...path]/route.ts:45-51`). The 8 MiB rule is documented in the 413 detail and in integration tests for small PNGs.
- **Demonstrated invariant / expected behavior:** Attachments larger than 8 MiB must be rejected without accepting unbounded in-memory payloads.
- **Trigger scenario:** An authenticated user (anyone with the instance password) posts a multi-hundred-megabyte file from the gallery, or any client hits `POST /patients/{id}/attachments`.
- **Execution / data path:** Browser → nginx/UI → Next Route Handler → FastAPI multipart → full `read()` → 413 or OOM. Docker `restart: unless-stopped` would bounce a crashed API; the UI waits on `service_healthy`.
- **Broken behavior:** The size limit does not bound memory (or proxy buffering) during the read.
- **Impact:** The clinic API (and possibly the Next proxy) can become unavailable until the process restarts. Anonymous callers cannot do this; staff sharing the instance password can, including by mistake.
- **Recovery / workaround:** Avoid oversized files; restart `vetapp-api` / `vetapp-frontend` if the processes are killed. Smaller JPEG/PNG/PDF uploads still work.
- **Recommended fix:** Enforce the 8 MiB cap while streaming (content-length check plus a bounded read loop) and configure a matching proxy/body limit so the process never materializes the extra bytes.
