## Error Map

### AUD-001 — Importing the checked-in food catalog overstates energy for low-energy foods by approximately tenfold

- **Severity:** high
- **Category:** state/data integrity
- **Location:** `apps/api/src/vetdietderm_api/catalog/energy.py:291` — `canonicalize_imported_me`; `apps/api/src/vetdietderm_api/catalog/import_products.py:119`; `apps/api/data/products_normalized.json:354`.
- **Evidence:** Import divides legacy energy by ten only above 1,000. The checked-in dataset still contains older per-kg-style calculated energy below that threshold. For example, lingonberry has ME 470; current `scripts/file.py:238` computes 47.0 kcal/100 g from that same row's macros. Import persists 470. Scanning positive rows marked calculated found **741 source rows** whose imported value remains approximately ten times the current normalizer's value. These are source-row counts, not a claim about deployed rows.
- **Demonstrated invariant / expected behavior:** Catalog ME and ration arithmetic use kcal/100 g as fed; the normalizer and runtime document this explicitly.
- **Trigger scenario:** Import the checked-in dataset, then add an affected food to a ration.
- **Execution / data path:** JSON → magnitude-based canonicalization → stored ME with `value_status='measured'` → `load_foods` → `resolve_me` accepts the number as declared → assessment and saved snapshot.
- **Broken behavior:** Units are guessed from magnitude. Low-energy per-kg values pass as per-100-g values. Import also discards the source `calculated` marker; 3,203 positive source ME rows carry that marker, though not all markers establish the same calculation provenance.
- **Impact:** Systematic incorrect energy totals and energy-normalized results across a substantial catalog subset; error is durably carried into saved plan snapshots. No clinical harm or production-row count is inferred.
- **Recovery / workaround:** Manually correct/avoid affected foods or normalize the dataset before import. Updating a food does not retroactively repair frozen plan results. There is no general UI workaround for identifying all affected entries.
- **Recommended fix:** Give the source an explicit unit/version and energy-method provenance; normalize by declared source units, validate against macros, and reject ambiguous rows. Preserve provenance and resolve synthesized ME using the intended runtime policy. Prepare a separately reviewed catalog repair and affected-plan assessment plan; do not blindly divide all ME again.

### AUD-002 — Vitamin E in catalog milligrams is compared and displayed as IU

- **Severity:** medium
- **Category:** functional correctness
- **Location:** `apps/api/src/vetdietderm_api/assessments/repository.py:16`; `apps/api/src/vetdietderm_api/standards/fediaf/v2025/assessment.py:814`; `apps/api/src/vetdietderm_api/standards/fediaf/v2025/normative_data.py:93`.
- **Evidence:** Catalog seed defines E in mg. Provider nutrients retain E in IU from the normative JSON. `load_foods` transfers only code/value/status, discarding catalog units. `_target_row` obtains its purported input unit from the provider nutrient, making the comparison IU→IU. A food with 20 catalog mg/100 g assessed at 100 g returned `ration_daily_amount=20`, `unit='IU'`, `status='met'`, target about 5.556 IU/day.
- **Demonstrated invariant / expected behavior:** `docs/Nutrient.md:147` explicitly requires `insufficient_context` for unconvertible vitamin E and prohibits silent mg/IU comparison.
- **Trigger scenario:** Assess a food with a known E value using the catalog's documented mg unit.
- **Execution / data path:** PostgreSQL catalog number → unitless `FoodValue` → normative IU nutrient definition → identity conversion → numeric verdict and snapshot.
- **Broken behavior:** The provider's target-unit dictionary is substituted for the input food's unit, so the conversion guard never sees the real mismatch.
- **Impact:** A confirmed incorrect vitamin E unit and unsupported nutrient verdict; this audit does not infer a particular biological conversion without chemical-form data.
- **Recovery / workaround:** Treat existing E verdicts as unreliable; clinician must check the value separately. Other nutrient results need independent assessment of their own units.
- **Recommended fix:** Preserve canonical catalog input units in the food/provider boundary, or explicitly map the input dictionary before calculation. Emit `insufficient_context` until a supported form-specific conversion is available. Add a catalog-to-provider E regression case.

### AUD-003 — Import accepts impossible food composition and exposes it as measured catalog data

- **Severity:** medium
- **Category:** state/data integrity
- **Location:** `apps/api/src/vetdietderm_api/catalog/import_products.py:150`; `apps/api/data/products_normalized.json:14523`.
- **Evidence:** The Acari ciar BEEF MAINE COON row contains CH -957, MO 1000, DM -900, all on a per-100-g basis. Actual import into isolated SQLite committed these exact values, all with measured status. Non-ME import checks type but not sign/range; ORM and migration definitions have no value-range constraint preventing them.
- **Demonstrated invariant / expected behavior:** Per-100-g composition must have physically meaningful mass values. API nutrient-write validation already requires nonnegative values; runtime proximate-energy calculation rejects macros outside 0–100.
- **Trigger scenario:** Import the checked-in food dataset or a similarly malformed row.
- **Execution / data path:** Source number → direct Decimal insertion → catalog serialization and matrix → assessment input. ME fallback rejects this proximate composition, but does not repair the stored/catalog values.
- **Broken behavior:** The operator import bypasses the validation enforced by the API and labels invalid/derived numbers measured.
- **Impact:** Nonsensical catalog composition is persisted and shown; affected foods cannot yield a valid fallback energy result. No claim is made that every negative derived archival column is an atomic nutrient.
- **Recovery / workaround:** Correct or quarantine affected rows and reimport after validation; current production presence must first be checked.
- **Recommended fix:** Share appropriate canonical-data validation between import and API, check nonnegative atomic values and mass bounds, retain unknown/calculated distinctions, and report rejected rows before committing a batch.

### AUD-004 — Confirming an owner visit makes its copied files invisible to the clinician

- **Severity:** medium
- **Category:** state/data integrity
- **Location:** `apps/api/src/vetdietderm_api/visits/repository.py:161` — `copy_gallery`; `apps/api/src/vetdietderm_api/attachments/repository.py:78`; `apps/api/src/vetdietderm_api/owners/router.py:36`.
- **Evidence:** Visit routes use plain `owner_db` sessions. `copy_gallery` calls the clinical attachment creator without assigning `tenant_id` or `created_by`. Ownership stamping exists only on `TenantSession`. The copied row therefore commits with both ownership columns NULL. An isolated request/upload/confirm scenario returned 200, then clinician gallery `[]` and attachment-file 404, while owner file listing contained the row.
- **Demonstrated invariant / expected behavior:** Confirmation copies owner-request files into the accepted patient's clinician gallery; clinical rows must retain invitation-workspace provenance.
- **Trigger scenario:** Owner attaches a file before confirmation; clinician confirms the visit, including first-registration acceptance.
- **Execution / data path:** Owner request upload → plain session confirmation → new Attachment → NULL ownership → clinical `TenantSession` read criteria filter out the copy.
- **Broken behavior:** Reusing a tenant-dependent repository with a plain session silently omits ownership. `gallery_copied=True` then prevents a subsequent confirmation from repairing the copy.
- **Impact:** Clinician cannot manage or download the promised gallery copy through the clinical attachment API. Original request download remains a practical workaround; this is not a claim of physical file loss.
- **Recovery / workaround:** Download the original request file; repair ownership of affected copies using verified patient/workspace provenance.
- **Recommended fix:** Make the application-level copy operation require explicit ownership derived from the verified patient/invitation, or use a correctly scoped session. Test both personal and organization copies through the clinician read API.

### AUD-005 — Editing shortly after completion can autosave a completed encounter back to draft or in-progress

- **Severity:** medium
- **Category:** concurrency/idempotency
- **Location:** `apps/clinic-web/src/app/_components/encounter-workspace.tsx:247`; `apps/clinic-web/src/features/encounters/hooks.ts:40`.
- **Evidence:** Save status is derived from `editingRecord` in query data. Mutation success only invalidates the encounter/list/appointment queries; it does not publish `saved.status` into either cache or a local authoritative status. Completion sets the form fingerprint and encounter ID, but not persisted status. Autosave fires after 1,100 ms on a subsequent edit and uses whichever old query record is still available.
- **Demonstrated invariant / expected behavior:** Completing a visit persists completed status; fixing a typo afterward must not implicitly reopen it. UI completion also updates the appointment to completed.
- **Trigger scenario:** Complete an existing draft/in-progress visit; edit a field while the refreshed list/detail response is delayed past the next autosave.
- **Execution / data path:** PATCH completed succeeds → old query record remains draft/in_progress → edit → autosave PATCH writes old lifecycle status → appointment can remain completed.
- **Broken behavior:** A stale read becomes the source of a subsequent state transition, despite the successful mutation response already containing the new status.
- **Impact:** Clinical record and calendar status disagree; a clinician's completed visit can silently reopen. This is an execution-path proof, not a newly added browser regression test.
- **Recovery / workaround:** Wait for query refresh before editing or complete again after refresh. A slow/failed refetch extends the vulnerable interval.
- **Recommended fix:** Update both encounter caches from the successful mutation response, or maintain last-successful status locally; only an explicit reopen should reduce lifecycle state. Cover completion followed by editing with deferred query responses.

### AUD-006 — Assessment can use an older nutrient value than the catalog matrix shows

- **Severity:** medium
- **Category:** functional correctness
- **Location:** `apps/api/src/vetdietderm_api/assessments/repository.py:33`; `apps/api/src/vetdietderm_api/catalog/repository.py:141` and `:179`.
- **Evidence:** Multiple values for a food/nutrient/basis with different sources are permitted. Matrix sorting/display choose newest `updated_at`. Assessment loads all matching values without ordering and overwrites a dictionary entry for each row. With two valid source rows, CP=12 newer and CP=3 older, reversing unordered SQLite reads changed assessment from 12 to 3 while explicit newest selection stayed 12.
- **Demonstrated invariant / expected behavior:** Catalog display and assessment should resolve the same canonical nutrient value under a defined source-selection policy.
- **Trigger scenario:** A food has more than one source value for the same nutrient/basis and an execution plan returns them in the opposite order.
- **Execution / data path:** Multi-source rows → explicit newest matrix selection versus unordered assessment query → last-row-wins dictionary → different ration input.
- **Broken behavior:** Database row order implicitly decides clinical calculation input. The schema's multi-source identity does not make those values unique by food/nutrient/basis alone.
- **Impact:** Displayed composition and saved/calculated composition can differ. Actual occurrence in deployed rows/query plans was not measured.
- **Recovery / workaround:** Keep only one active source value until a shared resolver is implemented; recompute affected plans only after a deliberate review.
- **Recommended fix:** Apply one deterministic source-selection policy to matrix, detail, assessment and energy preview, including a tie-breaker; retain provenance. If multiple active sources are unsupported, enforce that invariant instead.

### AUD-007 — Changing a booked visit's type leaves the owner cabinet showing the previous type

- **Severity:** medium
- **Category:** state/data integrity
- **Location:** `apps/api/src/vetdietderm_api/appointments/repository.py:105`.
- **Evidence:** Linked-request synchronization copies time, duration, status and updated timestamp, but omits `visit_type`. Reproduction changed a confirmed appointment from supervision to primary: staff PATCH returned primary; owner visit listing still returned supervision.
- **Demonstrated invariant / expected behavior:** The confirmed owner request represents its linked calendar appointment; both interfaces label the booked service by visit type.
- **Trigger scenario:** Clinician edits the visit type of an appointment created by owner-request confirmation.
- **Execution / data path:** Calendar PATCH → Appointment.visit_type updated → VisitRequest companion update omits type → owner listing serializes stale request type.
- **Broken behavior:** Two persisted representations of the same booking disagree.
- **Impact:** Owner sees the wrong booked service after clinician changes it. Snapshot questionnaire answers may intentionally remain historical and need not be rewritten.
- **Recovery / workaround:** Explain the change separately or repair the request metadata; refresh does not fix a persisted mismatch.
- **Recommended fix:** Synchronize the booked type or derive current booking metadata from the linked appointment, while preserving the original questionnaire snapshot explicitly.

### AUD-008 — The 8 MiB clinician upload limit is checked only after an unbounded memory read

- **Severity:** medium
- **Category:** material performance
- **Location:** `apps/api/src/vetdietderm_api/attachments/repository.py:71`.
- **Evidence:** `upload.file.read()` is called without a size before `len(payload)` is compared with the 8 MiB cap. A probe recorded `read(-1)` and only then 413. Owner media/visit upload implementations already use bounded `MAX_ATTACHMENT_BYTES + 1` reads. The Next proxy streams the request; no corresponding backend body cap is configured in repository code.
- **Demonstrated invariant / expected behavior:** Rejecting an oversized file should not require materializing arbitrarily more than the supported payload size in application memory.
- **Trigger scenario:** Authenticated staff upload a very large JPEG/PDF, accidentally or deliberately, through the clinical gallery endpoint.
- **Execution / data path:** Multipart spooled file → unbounded bytes allocation → post-allocation check → 413 or memory pressure/process termination.
- **Broken behavior:** The advertised limit bounds accepted storage, not the read allocation.
- **Impact:** Large concurrent uploads can impair the single API process. Actual nginx limits and OOM thresholds are unknown; no production outage is claimed.
- **Recovery / workaround:** Resize files before upload; restart after a memory-related process failure if necessary.
- **Recommended fix:** Use a bounded read or streaming byte counter with early rejection; align any deployed proxy limit after verifying configuration. Apply the same upload primitive across the three upload paths.

### Data Validation Results and Reference Checks

- Product dataset: **3,771 rows / 3,686 distinct names / 85 repeated-name groups**. All repeated-name groups contain a difference; several differ only in category/type. `_normalized_products` at line 61 keeps the last name match, so import collapses 85 source records. This is not automatically a nutrient-conflict defect: define whether multi-category foods should be one entity or separate variants. One observed example changes fish oil from ingredient/fat to supplement, which also changes fallback-energy applicability.
- Across source numeric columns, 57 negative entries were found; many are derived ME/DM/ratio fields and are not imported atomic nutrients. The concrete imported invalid mass fields are covered by AUD-003. The `calculated` list is metadata, not an invalid numeric field.
- Runtime and archived normative JSON are semantically equal and pass the checked-in schema. Runtime source SHA-256: `4797426a18945c6ed5ba231619c8086c42fa6193640f07e62059e89bb0368caa`.
- Selected protein/mineral rows and bases were compared with the official [FEDIAF September 2025 publication](https://europeanpetfood.org/wp-content/uploads/2025/09/FEDIAF-Nutritional-Guidelines_2025-ONLINE.pdf), tables III-3b (printed p.16) and VII-11 (p.58). For example, the daily reference protein values are 4.95 for dog and 6.25 for cat per metabolic bodyweight; canonical mineral conversion and wet/dry selenium handling passed existing golden tests. This does not certify all normative records.
- Auto-selected adult profiles use published-per-1000-kcal targets scaled by working energy. VII-11 metabolic-bodyweight profiles remain reference data, consistent with current `docs/Nutrient.md`; their existence alone is not evidence that the active resolver is wrong.
- No actual PostgreSQL row inventory was obtained. A follow-up data inspection needs read-only queries for invalid macro ranges/nonfinite values, duplicate active food/nutrient sources, attachment ownership mismatches, linked visit/appointment disagreement, missing files, and affected saved-snapshot provenance.
